# 架构决策

本文回答一个具体问题：**中台接入多个模块，需要开多个端口、上 Docker 或虚拟机吗？**

结论先说：**都不需要。** 下面是理由和边界。

---

## 一、为什么不需要多端口

中台的定义就是**单一入口**。如果每个模块各开一个端口，那你得到的是"N 个独立服务 + 一个书签页"，
那叫导航页，不叫中台。中台的价值恰恰在于：

- 一次登录，走遍所有模块（不用每个工具记一套账号）
- 一套样式，视觉与交互一致
- 一份审计，谁在什么时候动了什么，集中可查
- 一处升级，改内核即全局生效

### 那模块怎么接进来

关键认知：**"多个模块"不等于"多个服务"。** 按模块的实际形态分四种接法：

| 模块形态 | 接法 | 对外端口 | 说明 |
|---|---|---|---|
| FastAPI 应用 | 同进程 `include_router` / `mount` | 复用中台端口 | 最理想，零额外开销 |
| Flask / WSGI 应用 | 子进程 + 内部端口 + 反代 | 复用中台端口 | Flask 与 FastAPI 不能共存于一个事件循环，必须进程隔离 |
| 纯静态前端（React/Vue 产物） | 中台托管静态文件 | 复用中台端口 | 只读资源，直接喂给浏览器 |
| 外部/异栈服务 | 子进程 + 内部端口 + 反代 | 复用中台端口 | 中台只做转发，不侵入 |

**只有"内部端口"这一层存在，且只绑 `127.0.0.1`**，局域网访问不到，用户也无感——
他看到的永远是 `http://127.0.0.1:8731/...`。

### 为什么 Flask 模块不能塞进同一个进程

FastAPI 跑在 ASGI 上，Flask 是 WSGI。理论上可以用 `WSGIMiddleware` 把 Flask 挂进 ASGI，
但会丢两样东西：

1. **WebSocket 不可用**——WSGI 协议根本不支持，OpsGen 的实时执行输出会失效
2. **中间件与生命周期语义错位**——两边各有自己的异常处理和启动钩子，混在一起出问题极难排查

OpsGen 是 Flask + flask-socketio，所以它走"子进程 + 反代"这条路。

## 二、为什么不需要 Docker

### 容器解决的是什么

Docker 解决的是**环境隔离与一致分发**——"我这儿能跑，他那跑不起来"。
它的代价是：多一层抽象、多一套运维、多一份资源占用。

### 本场景为什么不匹配

| 判断项 | 实际情况 |
|---|---|
| 需要环境隔离吗 | 四个模块都是 Python，各自独立 venv 即可隔离；其中两个同进程挂载，连 venv 都不需要 |
| 需要跨机一致分发吗 | 当前是单机自用；将来分发用 `start.bat` 重建环境足够 |
| 需要编排多个服务吗 | 不需要。是"一个前台 + 两个内部子进程"，不是微服务集群 |
| 代价 | **Docker Desktop on Windows 依赖 WSL2，常驻 2–4 GB 内存**；虚拟机更重 |

对一台个人工作站来说，为了跑三个 Python 脚本而常驻几 GB 内存，是明确的负收益。
**运维的第一原则是不引入没有收益的复杂度。**

### 什么时候才真的需要

| 场景 | 方案 |
|---|---|
| 某个模块只能在 Linux 跑（依赖 bash、systemd 等） | 用 **WSL** 跑那一个模块，中台反代过去。仍然不需要 Docker Desktop |
| 要做成团队共享服务、多机部署 | 那时上 Docker + 编排，且应放在服务器上，不是你的工作站 |
| 需要严格的版本隔离（同一模块要跑多个不兼容版本） | 用 Docker |

**现在一条都不成立。** 如果将来要练 Docker，建议用真实需要它的场景练——在这个项目上强行上容器，学到的会是错误的适用判断。

## 三、模块接入规范

> 完整字段说明、四种形态的取舍、排障手册见 **[MODULES.md](MODULES.md)**。
> 这一节只讲清「为什么这么设计」。

模块放在 `modules/<module_id>/`，其中 `module.py` 声明自己的接入方式：

```python
# modules/opsgen/module.py
MODULE = ModuleSpec(               # ModuleSpec 由中台注入，模块不需要 import 中台
    id="opsgen",                   # 唯一标识，必须等于目录名
    name="运维脚本生成",              # 导航显示名
    kind="subprocess_proxy",       # native | static | subprocess_proxy | external
    mount="/opsgen",               # 中台对外路径
    order=20,                      # 导航排序
    # subprocess_proxy 专用
    runner="flask_app",            # 中台提供的启动壳（不是模块里的文件）
    app_module="app",
    app_object="app",
    socketio_object="socketio",
    internal_port=8732,            # 只绑 127.0.0.1
    health_path="/",
)
```

### 为什么是「中台注入 ModuleSpec」而不是「模块 import 中台」

模块目录必须能脱离中台源码独立存在 —— 第三方模块随时会被 `git pull` 换成上游新版，
它自己并不知道中台包叫什么、装在哪里。如果加载方式要求
`from core.modules import ModuleSpec`，就得先把中台塞进它的 `sys.path`，
等于在导入期就把两边绑死，将来想把模块单独拷走都拷不动。

所以加载器把 `ModuleSpec` 这个名字直接注入一个干净的命名空间，再把 `module.py`
的源码 `exec` 进去。`ModuleSpec(...)` 照样解析得到，但模块既没 import 过中台，
中台也没进过它的 `sys.modules`。

### 四种 `kind` 的语义

| kind | 中台做什么 | 模块需要改造吗 |
|---|---|---|
| `native` | `include_router` 挂载 | 需要（提供 FastAPI router） |
| `static` | 托管前端产物 | 不需要，但要提供构建产物 |
| `subprocess_proxy` | 拉起子进程 + 反代 + 生命周期管理 | **不需要，原样运行** |
| `external` | 只反代，不管进程（模块自己启动） | 不需要 |

**优先选 `subprocess_proxy`**：第三方模块零改造，且能随时替换上游版本。

### 启动壳：为什么监听地址不由模块决定

上游代码里 `host="0.0.0.0"`、`debug=True` 是极常见的默认值。前者把内部端口
暴露到所有网卡，绕开中台全部鉴权；后者带的 Werkzeug 调试器本身就是一条
现成的命令执行链。但「不改第三方源码」同样是硬约定，否则没法跟上游同步。

两者同时满足的办法：**根本不执行模块的 `__main__` 分支**。
`import app` 只触发模块级代码，中台用自己的壳去拿它的 `app` 对象，
再由壳决定怎么起服务 —— 壳里的 `HOST = "127.0.0.1"` 是写死的，
环境变量和命令行都改不动它。

可验证结果：上游 `app.py` 里 `host="0.0.0.0"` 原封不动，
`netstat` 看到的是 `TCP 127.0.0.1:8732 LISTENING`。

### 子进程的生命周期

中台启动 → 按 `order` 依次拉起模块（**后台进行，不阻塞首页**）→
轮询 `health_path` 直到就绪（带超时）→ 写导航；
中台退出 → 按相反顺序终止子进程。

有三件事必须做对：

1. **端口占用检测**：启动前先探测 `internal_port`，被占用时要**明确报错并指出
   是哪个 PID 占的**，而不是让模块静默失败后收到一堆莫名其妙的 404。
   如果端口被占但健康检查能通过，就当作「上次残留的进程」直接接管，
   并在卡片上标注 —— 但中台退出时不会去杀它（它不是中台拉起的）。
2. **进程回收**：Windows 上 uvicorn 是**父 + 子同名进程**，只杀父进程会留下孤儿；
   统一用 `taskkill /F /T` 按进程树回收。
3. **半死进程不留**：启动了但探活超时，要把那个半死的子进程收掉，
   否则它占着端口，用户重试也是失败。

## 四、统一鉴权怎么处理

模块各自有登录体系（模块三有 JWT + Cookie），中台有自己的令牌。四条原则：

1. **模块的登录页不出现在中台导航里**——用户不该感觉自己在"切换系统"
2. **模块的内部端口不得直接暴露**，否则绕过中台就能访问
3. **浏览器要能不靠自定义请求头拿到模块的子资源**（CSS/JS/图片/表单都带不上头）
4. **但绝不能让中台令牌落进模块页面**

第 3、4 条同时成立，靠的是**模块级票据**，而不是把中台令牌拼进 URL：

| | 中台令牌 | 模块票据 |
|---|---|---|
| 存放 | 只走请求头 `X-LocalDeck-Token` | `HttpOnly` Cookie，`Path=/opsgen` |
| 作用域 | 整个中台 | 仅这一个模块的路径 |
| URL 里会出现吗 | 不会 | 只在进门那一次用 `?_t=`，随后换 Cookie |
| 泄露后果 | 中台失守 | 只能访问那一个模块自己的路径 |

在模块路径下，**连 `?token=` 形式的中台令牌都拒收**。原因是 URL 查询串是
第三方 JavaScript 读得到的地方，而中台自己的前端压根不需要用 URL 传令牌
（它走请求头），所以收紧这一条不损失任何功能。

### 已知残余风险（留给下一阶段）

反代能隔离**凭据**，但隔离不了**来源**：模块的 iframe 与中台首页同属
`http://127.0.0.1:8731`。同源意味着模块脚本理论上能碰到父页面的东西，
包括 `sessionStorage` 里的中台令牌。

这在「单一入口」前提下是天然存在的，不是实现疏漏。**处理方向是来源隔离**：
让模块内容从另一个回环端口提供，使 iframe 成为真正的跨源，浏览器自己就会
把两边隔开。这不违背「单一入口」（用户永远只输入 8731），代价是模块内容
不再经过中台的代理，需要另想办法保住转发层的审计。

这一条属「统一导航与鉴权」阶段的决策项，落地前先量清楚：现在是 3 个模块、
其中 2 个是自家代码，为它多引入一层是否需要。

## 五、安全边界（不得放宽）

1. 中台只绑 `127.0.0.1`；模块的内部端口同样只绑 `127.0.0.1`
2. 模块的第三方代码要按"不可信"对待——接入前审一遍它的启动参数
   （例如 OpsGen 默认 `debug=True`、`host="0.0.0.0"`，**接入时必须改掉**）。
   改法不是去改上游源码，而是让中台的启动壳接管监听地址 —— 见第三节
3. 反代不得转发到中台自身命名空间，避免循环
4. 任何"执行脚本/命令"的能力，必须配白名单 + 逐次确认，不能顺手开放。
5. **模块的实时通道默认不放行。** 第三方工具挂在 WebSocket / socket.io 上的
   功能，绝大多数就是「在服务器上执行脚本」——那是任意命令执行入口。
   OpsGen 的 `execute_script` 事件正是如此（把脚本写进临时文件然后 `bash` 执行）。
   默认阻断时会给用户一句说人话的说明，而不是静默失败。要开必须补白名单 +
   逐次确认 + 参数模板，三样缺一不可
6. **外部 CDN 资源默认剥离**，对应「零网络上传、无遥测」。
   代价通常是装饰性的（代码高亮、字体），功能不受影响
7. 转发前独立校验路径：拒绝 `..`、反斜杠与非法字符集。
   安全不能寄望于「上游不会构造出奇怪的路径」
8. 模块的会话 Cookie 作用域被收进它自己的 `Path`；中台令牌在任何情况下
   都不落进 URL、不进 Cookie、不进模块

## 六、外观配置为什么这么存

品牌信息（名称、Logo、配色、背景图）由用户在界面上改。四个决策：

### 存哪儿：SQLite 的 `meta` 表，不落独立 json

README 承诺"备份 = 拷一个 db 文件"。加一个 `branding.json` 就把这个承诺破了。
`meta` 本来就是键值表，正好放这类"平台级单例配置"。

### 图片怎么存：data URL 内联，不落地成文件

同样是为了上面那条承诺。另外还免掉一整套静态资源路由**和它的鉴权例外**——
独立图片路由要么免令牌（那图谁都能取），要么带令牌（但 `<img src>` 和 CSS
`background-image` **带不上自定义请求头**，图根本加载不出来）。

代价是首页 HTML 随图片变大，所以设了体积上限（原图约 620 KB / 1.2 MB）。
本地回环传输，这点体积是毫秒级的。

**只收位图，拒收 SVG。** SVG 能内嵌脚本。虽然用作 CSS `background-image` 时脚本不会执行，
但少一个可以被绕的入口，比事后解释"为什么这样也安全"要划算。

### 配色怎么下发：只给 5 个基色，派生色用 `color-mix()` 现算

服务端只注入 `--accent / --accent-2 / --bg / --surface / --text`，
浅色底、描边、发光、阴影这些派生色全部在 CSS 里算。

好处是：用户拖取色器时整页配色实时跟随，不需要在 Python 和 JS 里各维护一套配色公式，
也不用每次改动都重新生成一遍 CSS。

### 为什么在服务端注入，而不是前端拿到配置再改样式

否则会先闪一下出厂配色、再跳成用户的——首屏那一下很难看。
服务端直接写进 `<style>`，页面带着正确配色首屏渲染。

### 免令牌的边界

`GET /api/branding` **免令牌**：首页在拿到令牌之前就要用它渲染配色，
且这个接口只吐"平台长什么样"，不含任何本机数据。
能打开 `127.0.0.1:8731` 的人，本来就能在页面上看到这些，不构成新增泄露面。

`PUT /api/branding`、`POST /api/branding/reset` **必须带令牌**。

所以 `security.needs_token()` 是**按「路径 + 方法」双重判断**的，不是只看路径——
同一个 `/api/branding`，读放开、写收紧。
